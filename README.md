
## Лабораторная 4 — вёрстка

### Цель работы

Создать семантическую и адаптивную вёрстку сайта «АгроМаркет» с использованием HTML5, Flexbox и CSS Grid.

### Box model карточки (часть 1)

Карточка товара использует CSS-свойство `box-sizing: border-box`.

- Content: зависит от ширины колонки каталога.
- Padding: 16px.
- Border: 1px.
- Margin: 0.

При `box-sizing: border-box` внутренние отступы и границы включаются в заданную ширину элемента.

### repeat(4, 1fr) на узком экране (часть 4)

При фиксированной сетке из четырёх колонок карточки сильно сжимаются на узком экране.

Для адаптивной сетки используется `repeat(auto-fit, minmax(...))`, позволяющий автоматически изменять количество колонок.

### auto-fit vs auto-fill (часть 4)

`auto-fit` позволяет существующим карточкам занимать свободное пространство.

`auto-fill` сохраняет место для дополнительных колонок, даже когда товаров недостаточно для их заполнения.

Для каталога выбран `auto-fit`.

### Форма заявки (часть 6)

Добавлена форма оптовой заявки с HTML5-валидацией.

Проверены следующие случаи:

- Пустые обязательные поля — браузер запрещает отправку.
- Некорректный email — появляется сообщение об ошибке.
- Объём заказа менее 10 кг — браузер требует исправить значение.
- Корректные данные — появляется сообщение об успешной отправке.

## Тестирование

Требуется Node.js 22 или новее. После клонирования: `npm ci`.

- `npm test` — Vitest + Testing Library, один прогон.
- `npm run test:watch` — интерактивный Vitest.
- `npm run coverage` — V8 coverage, HTML в [coverage/index.html](coverage/index.html).
- `npx playwright install chromium` — установка браузера для E2E.
- `npm run e2e` — Playwright; по умолчанию frontend на localhost:5173, backend должен быть доступен по VITE_API_URL.

Production, PowerShell:

```powershell
$env:E2E_BASE_URL = 'https://agromarket-react.vercel.app'
npm run e2e
Remove-Item Env:E2E_BASE_URL
```

Playwright создаёт только собственного уникального покупателя и учебную заявку; существующие записи не изменяет и не удаляет. Повторный запуск buyer и CI retry могут создать ещё одного пользователя. Корзина в текущем приложении — счётчик, оптовая заявка не связана с выбранным товаром. Router отсутствует: /login и /admin возвращают ту же SPA; гостю доступна форма входа, форма добавления товара скрыта.

[CI](.github/workflows/ci.yml): npm ci → npm test → lint → build на PR и push main. [E2E workflow](.github/workflows/e2e.yml): вручную и ежедневно в 04:00 UTC (09:00 Asia/Qyzylorda), Chromium, один retry в CI. При ошибке отчёт и trace сохраняются на 7 дней. E2E не запускается на каждом PR: проверяет уже опубликованную версию, зависит от внешних сервисов и создаёт записи в production. Отчёты могут содержать данные тестового аккаунта; не публикуйте их в Git.

### Полные E2E: только локальная тестовая среда

Нужен существующий backend в `agromarket-server` (или E2E_BACKEND_DIR), его зависимости `npm ci`, Chromium (`npx playwright install chromium`) и **отдельная локальная PostgreSQL agromarket_test**. Настройки находятся в игнорируемом `.env.e2e`; пример — `.env.e2e.example`. Настоящие пароли/JWT в Git не добавляются.

Для этой работы подготовлены PostgreSQL 18.6 на `127.0.0.1:55432`, ICU locale ru-RU, тестовый admin и случайные локальные секреты. VM из прежней .env.test была недоступна; рабочие .env backend и production-настройки не менялись. Официальные [PostgreSQL binaries для Windows](https://www.enterprisedb.com/download-postgresql-binaries) распакованы в игнорируемую `.lab12-local/pgsql`. Для другого компьютера можно указать `-PgBin` с каталогом bin установленной PostgreSQL.

```powershell

npm run e2e
npx playwright show-report
```

Скрипт PowerShell совместим с Windows PowerShell 5.1, сохранён в UTF-8 с BOM. Не перезаписывает существующий .env.e2e при создании нового кластера. PostgreSQL запускается отдельно; Vite на 5173 и настоящий Express на 3100 Playwright запускает и останавливает сам. **Каждый локальный прогон seed пересоздаёт таблицы только agromarket_test. Существующая серверная роль `admin` единственная может создавать товары. Поэтому E2E_FARMER_EMAIL/PASSWORD содержат данные локального тестового администратора. Роль farmer и Router не внедрялись ради примеров методички.

### Ответы по выполненной работе

1. **Что обнаружили компонентные тесты.** ProductCard не показывал переданную API категорию — добавлено отображение и тест. Каталог не позволял повторить запрос после сбоя — добавлены кнопка и проверка перехода 500 → успех. Сохранились изображения, корзина и прежние сценарии.

4. **Пустой каталог.** Handler возвращает настоящий формат API — пустой массив. Проверяется «Товаров нет»; HTTP 500 не должен давать такое же состояние.
5. **HTTP 500.** Показывается понятная ошибка с role=alert и повторной загрузкой; отдельный тест возвращает успешный handler на втором запросе. Сетевая ошибка проверена отдельно через HttpResponse.error().
6. **Почему MSW.** Он перехватывает запрос на сетевом уровне, сохраняя настоящий apiFetch, URL, JSON, заголовки и разбор статуса. Старые узкие vi.mock/fetch-spy сохранены, но не заменяют сетевые тесты. Настроены resetHandlers, cleanup, clear localStorage и onUnhandledRequest:error.
7. **Почему не production.** Регистрация/товары/заявки меняют настоящие данные. ЛР12 выполняет их только на локальной agromarket_test. На внешних хостах даже ошибочный полный запуск запрещён конфигурацией.
8. **Smoke и E2E.** Smoke — два коротких read-only сценария доступности уже опубликованной системы. Полные E2E проходят запись и взаимодействие всех настоящих локальных слоёв. MSW-прогон не называется полноценным E2E.
9. **Trace.** Изменён regex заголовка на Intentional-Lab12-Wrong-Title. Trace показывает успешную загрузку и падение toHaveTitle через 1000 мс; реальное название — «АгроМаркет — фермерские продукты». Screenshot подтверждает видимые товары. Trace исследован по JSON-событиям/сети, screenshot просмотрен; интерактивный Viewer не использовался. Правильное ожидание восстановлено; 7 E2E снова прошли.
10. **Цена -500.** Форма остановлена HTML rangeUnderflow до POST. При прямом запросе с admin JWT Express/Zod вернул реальный HTTP 400 details.price. MSW отдельно проверяет показ «Цена должна быть больше 0» без вызова onAdded/ложного успеха.
11. **Два уровня валидации.** Клиент помогает пользователю сразу; его min можно обойти запросом вручную. Поэтому сервер проверяет данные независимо. Тесты подтверждают обе границы, а не только текст ошибки.
12. **GitHub Actions.** Существующий CI / build на Node.js 22 выполняет npm ci, lint, test:run, build. Имя build сохранено для существующей branch protection; новый дублирующий workflow не создавался.
13. **Красный CI и merge.** В PR #11 ожидание цены 451 тг вместо 450 привело к FAILURE check build. GitHub API до закрытия показал mergeStateStatus=BLOCKED; защита main требует build и актуальность ветки. PR закрыт без слияния, обход не выполнялся. enforce_admins=false: технически администратор может обходить правило; это ограничение честно зафиксировано. Человеческое ревью ещё не получено.
14. **Использование Codex.** Аудит реальной архитектуры, добавление MSW и тестов, два исправления UI, настройка безопасной тестовой PostgreSQL, реальные прогоны и анализ ошибок, trace/screenshot, обновление CI, создание логических коммитов и PR, документация. Codex не имитировал ревью напарника и не изменял production-данные.
