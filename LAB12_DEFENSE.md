# Лабораторная 12 — ответы для защиты

Ответы относятся к существующему «АгроМаркету»: React/Vite, App.jsx, LoginForm, ProductCard, Express/PostgreSQL. React Router и AuthContext специально для тестов не добавлялись. Код тестов — в PR [#10](https://github.com/sarov1713-hub/agromarket-react/pull/10).

## 1. Компонентный тест, E2E и пирамида тестов

Компонентный тест проверяет компонент или несколько связанных компонентов в изоляции от настоящего API. Например, RTL рендерит LoginForm, пользователь вводит данные, MSW возвращает HTTP 401, тест проверяет сообщение и отсутствие авторизации.

E2E использует настоящий Chromium, Vite, Express и отдельную PostgreSQL. В нашем сценарии пользователь входит как администратор, создаёт товар через форму, видит его цену в каталоге, после чего тест удаляет товар через API.

Пирамида означает много быстрых узких проверок и меньше дорогих сквозных. Сейчас выполнено 82 backend-теста, 37 frontend-тестов и 7 локальных E2E. Два production smoke проверяют доступность опубликованного сайта и не изменяют данные.

## 2. Что делает jsdom

jsdom предоставляет DOM, события и browser-like API в Node.js. Vitest использует `environment: 'jsdom'`, RTL рендерит React в этот DOM. Однако jsdom не является браузером: нет полноценной раскладки, отрисовки, реальных изображений и всех особенностей HTML-валидации. Поэтому доступность формы и обработчики удобно проверять в RTL, а реальные переходы, браузерную валидацию и сеть — в Playwright.

## 3. Почему рекомендуются роли и подписи

`getByRole('button', { name: 'Войти' })` и `getByLabelText('Email')` описывают интерфейс глазами пользователя и вспомогательных технологий. Они меньше зависят от CSS и внутреннего устройства React. Если поле нельзя найти по подписи, это может выявить проблему доступности.

В LoginForm уже были корректные `label htmlFor` и `input id`; переписывать их не понадобилось. В ProductCard добавлен testid для стабильного выделения карточки в E2E, но кнопки, поля и заголовки внутри неё по-прежнему ищутся по ролям и именам.

## 4. getBy, queryBy и findBy

- `getBy` синхронно находит существующий элемент и падает, если его нет. Подходит для начального состояния загрузки и полей формы.
- `queryBy` возвращает null, если элемента нет. Подходит для проверки отсутствия ложного успеха или формы администратора у покупателя.
- `findBy` ожидает появление элемента. Используется после HTTP-запроса: например, `await screen.findByRole('alert')`.

Обычно `getBy/queryBy/findBy` ожидают единственный элемент; для списков есть варианты `*AllBy`. Ожидание видимого результата надёжнее произвольного sleep.

## 5. Как работает MSW и чем отличается от vi.mock(fetch)

В Node-тестах используется `setupServer` из `msw/node`, в MSW 3 — `http`, `HttpResponse` и `delay`. Перехватывается реальный HTTP-вызов, а код `apiFetch` продолжает собирать URL, заголовки и JSON и обрабатывать статусы. Поэтому проверяется больше настоящего поведения приложения, чем при замене самой функции fetch.

Наши handlers соответствуют API: GET /products возвращает массив; login/register возвращают `{user, token}`; ошибка валидации содержит массив `details: [{field, message}]`. Старые узкие тесты с vi.mock(apiFetch) и три проверки с fetch-spy сохранены; каталог и новые сценарии ошибок/форм работают через MSW. Сетевые тесты не подменяют полноценные E2E.

## 6. Зачем сбрасывать handlers и localStorage

Тест HTTP 500 не должен оставлять ошибочный handler следующему тесту успешного каталога. Тест входа не должен оставлять токен следующему гостевому сценарию. Поэтому setup выполняет `server.resetHandlers()`, `localStorage.clear()`, `cleanup()` и восстановление spy. Сервер стартует с `onUnhandledRequest: 'error'`: неожиданный запрос считается ошибкой, а не уходит в настоящий API.

## 7. Автоожидание Playwright

Перед click/fill Playwright ожидает готовность элемента к действию, а web assertions повторяют проверку до таймаута. Наш smoke ждёт карточку до 75 секунд, чтобы учитывать холодный старт Render, без `waitForTimeout`. Для отправки формы ожидание `page.waitForResponse` создаётся до click, чтобы не пропустить быстрый ответ.

## 8. Зачем уникальный email

В PostgreSQL поле users.email уникально. Повторный запуск с тем же email может получить конфликт вместо успешной регистрации. Покупательский E2E формирует адрес из времени и randomUUID. Он используется только в локальной `agromarket_test`; teardown удаляет связанные заявки и пользователей с тестовым префиксом.

## 9. Почему полные E2E нельзя запускать на production

Регистрация, создание товара и заявки изменяют данные, засоряют рабочую БД и могут запустить реальные процессы. В ЛР12 эти действия выполняются только с локальными frontend/API и строго локальной БД `agromarket_test`.

Для внешнего адреса конфигурация разрешает только smoke.spec.js с меткой @smoke. Полный запуск на Vercel отклоняется ещё до браузера. Smoke дополнительно блокирует браузерные методы кроме GET/HEAD/OPTIONS. Старый unsafe production-workflow отключён до merge безопасной замены из PR #10.

## 10. Как rate limit из ЛР11 влияет на E2E

Лимит авторизации — 10 попыток за 15 минут; повторные E2E с одного IP могут получить 429 вместо ожидаемого результата. В существующем backend при NODE_ENV=test limiter отключается. Только в этом режиме выполняются локальные E2E, с отдельной БД и тестовыми секретами. Production-настройки не изменены. Поведение 429 проверяется отдельно через MSW и backend security-тесты, которые включают limiter в изоляции.

## 11. Зачем build в CI

Успешный тест jsdom не гарантирует, что Vite соберёт приложение: могут быть неверные импорты, ошибки конфигурации или отсутствующие ресурсы. CI выполняет `npm ci`, lint, одноразовый Vitest-прогон и production build на Node.js 22. Это проверяет путь к артефакту деплоя.

## 12. Что даёт Require status checks to pass

У main уже обязателен check `build`, включена актуальность ветки (`strict: true`). В экспериментальном PR #11 CI упал на ожидании 451 тг вместо 450 тг, а GitHub показал `mergeStateStatus: BLOCKED`. PR закрыт без merge. Настройка сохранена, force push и обход checks не использовались.

Важно различать защиту обычного merge и абсолютный запрет обхода: `enforce_admins: false`, поэтому владелец с административными правами технически может обойти правило. Мы этого не делали. Обязательных approvals в настройке 0, но методичка требует настоящее ревью напарника — оно остаётся незавершённым, пока человек не проверит PR.

## 13. Почему локально проходит, а в CI падает

Причины: другая ОС/версия Node, регистр имён файлов, незакоммиченные файлы, отсутствующие env, отличающийся lock-файл, локально сохранённый token, зависимость тестов от порядка, другой язык/локаль БД, сетевые задержки. `npm ci`, очистка хранилища, resetHandlers и запрет непредусмотренных запросов уменьшают эти различия.

В этой работе первая попытка backend-прогона на новой локальной БД дала 79/82: тестовый Origin отличался от ожидаемого localhost, а locale=C не обеспечивала нужное поведение ILIKE для кириллицы. Исправлена только изолированная тестовая среда (Origin и ICU ru-RU), после чего прошли все 82 теста. Сами проверки не ослаблялись.
